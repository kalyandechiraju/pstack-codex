01

The mental model

A workflow layer, not an app framework.

pstack teaches a coding agent how to investigate, design, delegate, verify and deliver. It is not a replacement for your application stack.

Think of it as an engineering operating procedure packaged as a Cursor plugin. The repository contains instructions in SKILL.md files, task playbooks, subagent definitions and supporting helpers. You keep your language, framework, tests and Git workflow; pstack changes how the agent approaches the work. R1R2R3

YOUGoal + checksWhat matters?
ROUTER/poteto-modeClassify the task.
PLAYBOOKOrdered stepsVisible todo list.
EXECUTIONSkills + agentsInvestigate and build.
DELIVERYEvidenceVerify, then review.
Your responsibility

Specify the outcome.

Give the goal, constraints, finish condition and permission boundary. Decide which trade-offs are acceptable. Inspect the evidence and the diff.

The plugin’s job

Supply the process.

Select a playbook, expose its steps, bring in specialist skills and delegate work. Skipped steps should remain visible with a reason. R3R10

i
The useful distinction

A good prompt says “make retrying safe, and prove only one record is written,” not “use five agents.” More generated code, more agents and more green checkmarks are not the same thing as a correct result.

02

First-time setup

Install once. Make verification project-specific.

Begin with a local Cursor agent in a development checkout. These are chat commands, not terminal commands.

1

Install the core plugin.

Open Cursor with the repository you intend to work on. Install pstack in chat and confirm its skills are available.

Cursor chat · installation
/add-plugin pstack
2

Add the companion tools.

The README recommends cursor-team-kit for the full workflow. Its code-cleanup and app-control skills are referenced by pstack but are not bundled inside it. R1

Cursor chat · recommended companion
/add-plugin cursor-team-kit
3

Choose models by role.

Run setup and choose from the models your account actually exposes. Then start a new chat so the generated model rule applies. R4

Cursor chat · configuration
/setup-pstack
User-level configuration

Model routing

Setup writes ~/.cursor/rules/pstack-models.mdc. It maps roles such as code delegates, judgment and review panels to models. Missing role entries retain the skill’s defaults. Re-run setup to change choices. R4

Project-local knowledge

App verification

A generated .cursor/skills/verify-<app>/ teaches agents how to launch and exercise this particular app. Create or maintain it per project, not once for every repository you own. R9

i
Do not memorize the current default model names

The defaults can change between releases and differ by role. Let setup discover your available models. inherit-parent and auto mean “omit the subagent model override”; they do not remove subagents or create model diversity. A panel’s configured list length determines its size. R4

What should you choose?

Suggested starting point: use a strong model for design and judgment, a faster available model for mechanical work, and a small review panel with different model families when available. Begin with a narrow task and inspect usage before expanding fan-out. This is a configuration recommendation, not a measured cost claim.

Setup offers to generate a verification skill when it finds neither one nor an existing harness. Accept for an app that already runs. For an empty repository, first create the runnable slice described below; the generator explicitly requires a working baseline. R4R9

!
Companion tools and integrations are separate

Installing pstack does not automatically provide your project’s dependencies, test accounts, database, simulator, GitHub authorization or every MCP integration. Make the development environment usable and grant only the access the task needs. The bundled Benny automation pack is dormant and needs separate setup. R1R9

03

Everyday usage

Write a brief, not an orchestration script.

Let the playbook choose the ceremony. Your words should carry the goal and the boundaries.

Goal+Known context+Must not change+Proof of done+Permissions
Cursor chat · example prompt
/poteto-mode add a watched filter to the existing movie list.
Keep the current ordering and persistence behavior unchanged.
Done means the filter works, its count is correct, and it survives a page reload.
Verify the real UI and show the commands and evidence.
Work locally only. Do not push, open a PR, merge or deploy.

This would normally enter the Feature playbook. That playbook covers investigation, design, decomposition, implementation delegation and verification. You do not need to repeat those steps manually. The local-only restriction is intentional: Feature otherwise ends by running Opening a PR. R3R10

SituationWhat to sayWhy it matters
Continue the same taskContinue and verify the remaining checks.The mode stays active in the current conversation until you opt out.
Change subjects/poteto-mode new task. …Forces a fresh task match rather than extending the previous playbook.
Investigate onlyRead-only investigation. Do not change code.Separates a question from authorization to implement.
Design before approval/architect with checkpoint. Stop before implementation.Architect otherwise normally continues into implementation.
Leave the modeStop using poteto-mode for this conversation.Explicitly opts out of the sticky behavior.

These are natural-language instructions, not extra CLI flags. Sticky mode is conversation behavior, not a guarantee of context across unrelated new chats. R3R6R12

i
Read the todo list and the final proof

Expect the selected playbook’s steps, explicit reasons for skipped steps, and a distinction between completed, failed and blocked checks. A confident “done” without executable evidence is not the output you are trying to train yourself to accept. R3R8

04

Path A · new projects

Start with one thin, verifiable slice.

Example project: a small movie-watchlist web app. The stack and prompts are illustrative; pstack does not require Next.js or TypeScript.

✓
The target for the first slice

A user can add, view and remove a movie; entries survive reload; duplicate additions are rejected. No login, recommendations, cloud sync or payments yet. That small boundary makes the first implementation and its evidence easy to inspect.

1

Choose the product boundary and the data shape.

Open a new Git repository. Tell the agent your stack and exactly which behavior belongs in the first slice. Ask for a design checkpoint when you want to inspect the proposed shape before any files change. R6

Cursor chat · example prompt
/architect with checkpoint. Design the first slice of a new movie-watchlist app.
Use Next.js and TypeScript. For this prototype, use browser-local persistence.
Support add, list and remove. Reject duplicate movie IDs.
Show the caller-facing usage, domain types, module boundaries and verification approach.
Exclude accounts, recommendations, cloud sync and payments.
Stop after the design. Do not implement, commit, push or deploy.
2

Build only the agreed slice.

After reviewing the design, authorize implementation. Ask for a launchable result and testable behavior, not a large framework of placeholders. A first end-to-end run can use the current harness; the reusable verification skill comes next.

Cursor chat · example prompt
/poteto-mode implement the approved watchlist slice in this local repository.
Keep the structure minimal and use the selected package manager consistently.
First get the app running, then complete add/list/remove and duplicate handling.
Done means these actions work in the real browser and persistence survives reload.
Add focused behavior tests where appropriate. Show what you actually ran.
No extra features. Do not push, open a PR, merge or deploy.
3

Teach the agent how to verify this app.

Once the checkout builds and launches, generate its reusable control-and-evidence instructions. The generator should reuse existing harnesses, discover the real controls and execute its own output once. R9

Cursor chat · example prompt
/create-verification-skill for this watchlist app.
Reuse the existing test and browser harness where possible.
Map adding, listing, removing, duplicate handling and persistence.
Use isolated development data. Prove one feature end to end,
then confirm its evidence still exists after cleanup.
4

Exercise the whole first slice.

The generator’s initial proof covers one mapped feature, not every feature in the app. Follow it with a deliberate pass across all first-slice behaviors. Use the generated skill’s actual name or refer to it in plain language. R9

Cursor chat · example prompt
/poteto-mode verify every feature in the watchlist verification map.
Add a movie, reject a duplicate, reload, remove it, and reload again.
Check both visible state and the persisted state that backs it.
Report PASS, FAIL or BLOCKED per behavior with evidence paths.
Do not quietly edit product code or weaken checks during this verification pass.
5

Review the change, then decide how to deliver it.

Ask for an independent critique. Interrogate returns a consolidated judgment; it does not automatically apply its findings. Decide which findings to fix before authorizing PR creation. R6R8

Cursor chat · example prompt
/interrogate review the watchlist changes against the original first-slice brief.
Focus on correctness, lost data, duplicate handling and unnecessary complexity.
Distinguish demonstrated problems from speculation. Review only; do not edit.
i
The next feature gets a new task, not a new scaffold

After this slice is reliable, add one capability such as a watched filter. Keep the app runnable, add the corresponding verification entry, and repeat. You do not reinstall pstack or regenerate the entire app for each feature.

05

Path B · existing projects

Understand the system before improving it.

Adopt pstack around your repository’s conventions. Do not let a workflow upgrade turn into an unrequested application rewrite.

1

Establish a read-only baseline.

Open the actual development checkout and identify its normal launch, test and lint commands. Record pre-existing failures separately from failures caused by the proposed change. Preserve unrelated local work.

Cursor chat · example prompt
/poteto-mode new task. Read-only onboarding to this existing repository.
Identify the main user flows, architecture boundaries, package manager,
run/test commands and relevant project instructions.
Inspect git status and report unrelated local work without changing it.
Run only safe local baseline checks using development data.
Separate existing failures from unknowns. Do not edit, upgrade, commit or publish anything.
2

Trace the subsystem, then its history.

Use how for present behavior and why for historical rationale. Why can consult source control and available connected evidence; it does not magically grant access to Slack, issue trackers or private docs. Missing history should remain a stated gap. R5

Cursor chat · example prompt
/how does a movie move from the UI into persistent storage?
Trace request handling, retries, deduplication and error reporting.
Name the actual files, types and side effects. Do not edit code.
Cursor chat · example prompt
/why was retry handling split between the client and the API?
Use only available, authorized sources. Separate recorded reasons from inference.
Do not invent the rationale if the history is missing.
3

Reuse the test infrastructure; fill the real gap.

An existing browser suite, CLI harness or service test setup is an asset. Create a project verification skill only where useful, and make it wrap the real run path rather than replacing the team’s checks. R8R9

Cursor chat · example prompt
/create-verification-skill for this repository.
Reuse its existing launch scripts, fixtures and test harnesses.
Focus first on the watchlist and retry flows. Do not add a parallel test framework.
Do not change product behavior. If the checkout cannot run, report the blocker first.
4

Make one scoped change in isolation.

Give the agent a fresh worktree or branch for the task, define the compatibility boundary and state what counts as proof. For a defect, insist on the reproduction before the fix. R7R12

Cursor chat · example prompt
/poteto-mode new task. Retrying add-to-watchlist sometimes creates two rows.
Use a fresh worktree from the repository's agreed base branch.
Reproduce the failure first, trace the root cause, then make the smallest correct fix.
Preserve the public API and support the existing released clients.
Done means a repeated request creates exactly one persisted row,
and independent requests still work. Verify the UI and storage side effect.
Do not upgrade dependencies or touch unrelated code.
Local changes and local commits only. No push, PR, merge or deployment.
5

Review the diff against the baseline.

Inspect the actual change, the regression test and the runtime evidence. Ask which checks could not run. Then explicitly authorize publishing a PR when you are ready, keeping merge and deployment as separate decisions. R8

Cursor chat · example prompt
/poteto-mode summarize the change against the original baseline.
List exact verification commands, results, evidence paths and remaining risks.
Show any unrelated edits and remove only the ones created by this task.
Stop for my review. Do not push, open a PR, merge or deploy.
!
Preserve compatibility where your product requires it

pstack favors simplification and deleting superseded internal APIs. That is not a license to break released clients, remove a required migration window or delete shared data. State those constraints explicitly. “Redesign from first principles” should not become an unrequested rewrite. R3

Good first adoption task

A reproducible small bug

A local input reliably triggers the wrong result. The team already has a way to run the affected feature. The intended fix and proof fit in one focused review.

Poor first adoption task

“Clean up the whole repo”

No baseline, no bounded behavior and no clear finish condition. Start by investigating the problem that supposedly makes the cleanup necessary.

06

The highest-leverage setup

Turn “it works” into a repeatable procedure.

A verification skill is the bridge between the code the agent edits and the product a user experiences.

The generator writes a project-local skill with Launch, Doctor, Drive, Evidence and Cleanup instructions, plus any needed helpers and a feature map. It must use real commands and selectors from the repository, not a template left full of placeholders. R9

Illustrative output · not a prescribed full file tree
.cursor/skills/verify-watchlist/     ← example generated name
  SKILL.md                          ← launch, doctor, drive, evidence, cleanup
  features/
    README.md                       ← feature index
    add-movie.md                    ← example feature entry
    remove-movie.md                  ← example feature entry
    persistence.md                  ← example feature entry
  ...                               ← helpers only when needed

Use the actual generated name in your repository. Each feature entry has four required headings: Sub-features, How to get to it (user POV), Driving it with <harness>, and Gotchas. The entry describes both the actions and their observable expected results. R9

ChangeUseful proofNot enough on its own
Web UIDrive the actual controls; capture the action and resulting state; check persistence where relevant.A build, a mock screenshot, or setting internal state directly.
CLI / TUIExecute the real command or terminal interaction; inspect stdout, exit status and written files.A helper function passing a unit test.
API / storageSend a real local/test request, inspect the response, then read back the side effect.Only asserting that the handler returned 200.
PerformanceCompare before/after on the same fixture and measurement harness.“The code looks faster” or a different dataset.
MobileUse the available simulator/device harness to exercise the changed flow and capture evidence.Claiming UI verification when no usable device or harness was available.

These are examples of applying the repository’s evidence rules. A green build is useful, but it does not replace checking the changed behavior. R8R9

!
One successful generated-skill run is not whole-app coverage

The generator proves one mapped feature end to end. Later task checks or a deliberately scoped full pass must exercise the rest. It also checks that cleanup preserves the proof artifacts; evidence deleted during teardown is not an acceptable handoff. R9

Keep the verifier honest as the app changes.

Cursor chat · maintenance
/maintain-verification-skill

Maintenance combines source inspection with a live pass over mapped features. Its documented outcomes are clean, changed or blocked. Corrections stay inside the verification skill’s directory; a discovered product regression should be reported, not hidden by rewriting the expected behavior. The changed outcome can produce a PR, so add a local-only boundary when that is what you intend. R8

A useful final handoffWhat changed → exact commands and outcomes → evidence locations → unverified or blocked checks → residual risks → current branch or commit. The branch/commit attachment is an additional recommended provenance check, especially after later edits.
07

The cookbook

Eight workflows you can adapt.

Each example separates the prompt, the reason it works and the evidence to expect. These are original practice prompts, not recorded pstack test runs.

8 workflows

01Add a feature without accidental scope creepA watched filter in the existing app
Feature → design → delegated implementation → verification

The app already works. You want one additional user behavior, not a new architecture.

Cursor chat · example prompt
/poteto-mode new task. Add All / Unwatched / Watched filtering to the movie list.
Keep existing ordering, movie IDs and persistence unchanged.
The selected filter should survive reload. Counts must match the visible dataset.
Verify each filter, an empty result, toggling watched status, and a reload.
Keep this change separate from recommendation or styling work.
Local work only. Do not push, open a PR, merge or deploy.

How to read this workflow

The playbook supplies the investigation and design steps. The invariants protect adjacent behavior, while the empty state and reload requirements make the finish condition more than a happy-path screenshot. R10R8

Expected evidence: A focused diff, behavior tests where useful, a live pass through every named state, and evidence that the persisted filter is the one restored after reload.
02Fix a retry bug at the actual causeDuplicate writes after a repeated request
Bug fix → reproduce → root cause → fix → real-surface proof

The reported symptom is “duplicate movies.” Do not assume the cause is the UI button, the server handler or the database.

Cursor chat · example prompt
/poteto-mode new task. A retried add request creates duplicate watchlist rows.
Capture a failing reproduction before changing product code.
Trace the path from the user action to the database write.
Use a cheap failing regression test when the existing harness supports it.
Prove that replaying the same request creates one row, while two distinct
valid requests still create their intended rows. Preserve the public API.
Use test data only. Work locally; do not publish or deploy.

How to read this workflow

This avoids a cosmetic fix such as disabling a button while leaving server-side retries unsafe. TDD is useful when the local test path is cheap; it is not a reason to replace the actual product proof with elaborate mocks. R7R8

Expected evidence: The original failure, an explanation tied to the responsible code path, the regression check failing before and passing after, and the resulting storage state.
03Optimize a measured slow pathSearch over a fixed 5,000-movie fixture
Perf issue → baseline → profile → change → compare

Use a concrete fixture and measurement target. The numbers below are example acceptance criteria, not results observed in this research.

Cursor chat · example prompt
/poteto-mode new task. Measure search latency on our fixed 5,000-movie fixture.
Save the baseline and measurement script before changing code.
Profile the measured bottleneck. Aim for p95 below 200 ms using 30 repeated
searches on the same machine, fixture and warm-up policy.
Verify identical search results and no material memory regression.
Do not lower the target or change the fixture to claim success.
Keep changes local and report a blocker if the target cannot be met.

How to read this workflow

A one-off fix belongs in Perf issue. Sustained iteration on a single metric can use Hillclimb, which keeps accepted improvements and rejects losing attempts against a frozen harness. Explicitly record measurement limitations. R7R3

Expected evidence: The rerunnable benchmark, before/after measurements, profiling evidence, unchanged correctness, and the residual gap when the target is missed.
04Compare designs before committing to oneClient cache versus server caching
Architect → arena → synthesized design → checkpoint

The expensive decision is the caching boundary. Ask for competing designs with a rubric rather than asking several agents to edit the same files.

Cursor chat · example prompt
/architect with checkpoint. Design caching for the movie-detail flow.
Compare a minimal client-side cache with a server-owned cache, including
whether we need a new cache at all. Use two design candidates for this task.
Judge invalidation correctness, stale-data behavior, operational burden,
and caller-facing simplicity. Show types and request flows.
Stop with the recommendation and trade-offs. Do not implement or publish.

How to read this workflow

Architect normally uses arena for design exploration. Arena gives candidates the same problem, judges them and combines the best ideas. A checkpoint prevents the synthesized design from becoming an implementation before you inspect it. R6

Expected evidence: A grounded comparison, a chosen base design, rejected alternatives with reasons, and explicit open product decisions. Design proposals are not runtime evidence.
05Audit a monorepo without shared-write collisionsOne read-only verification lane per package
Swarm → independent scopes → aggregated coverage report

You need broad coverage rather than multiple competing implementations of the same idea.

Cursor chat · example prompt
/swarm inspect every package under packages/ using its existing check command.
Use one worker per package and cap concurrent workers at three for this run.
Read-only audit: do not change files, update snapshots, install new versions,
or publish results externally. Identify shared services before running checks;
serialize those checks unless instances and test data are truly isolated.
Return one table: package, command, PASS / ISSUES / BLOCKED, evidence and gap.

How to read this workflow

The concurrency limit here is a natural-language request to the agent, not a claimed pstack CLI flag or hard billing limit. Swarm aggregates independent scopes; it does not use arena’s base-selection-and-grafting workflow. R6R3

Expected evidence: A complete package list, one outcome per package, exact checks and explicit dropouts. “Most packages passed” is not full coverage.
06Refactor an internal API without behavioral driftMigrate callers and remove a truly internal legacy API
Refactoring or large-task figure-it-out → small verified units

The replacement API is already agreed. The challenge is a complete, behavior-preserving migration, not a broad redesign.

Cursor chat · example prompt
/poteto-mode new task. Migrate the internal watchlist-store callers to
WatchlistRepository in an isolated worktree. Preserve observable behavior.
First inventory all callers and record the relevant fixtures.
Build a codemod if it materially reduces repetitive edits.
Done means zero runtime references to the old internal API, every relevant
fixture passes, the user flows still work, and the obsolete internal API is removed.
Do not remove public compatibility used by released clients.
Keep a decision log. Local commits only; do not push, merge or deploy.

How to read this workflow

The scope determines the route: a small structural change may stay in Refactoring; a cross-cutting migration may route through figure-it-out. A textual “zero matches” check alone is insufficient; the runtime and fixture checks must also pass. R3R7R11

Expected evidence: Caller inventory, before/after behavior, a reusable migration artifact when justified, and a decision trail for exclusions or compatibility that must remain.
07Review a PR, then control how far it proceedsStatus, fixes, merge-ready and merge are different permissions
Interrogate for review · Babysit for PR state · Shipping to land

Choose the action you actually want. A status request should not quietly turn into merging a green PR.

Cursor chat · example prompt
/interrogate review the current branch against its stated intent.
Focus on correctness, regression risk and maintainability.
Return the consolidated findings and explain dismissals. Do not edit.

Then, as a separate request when only status is needed:
/poteto-mode check on the current PR. Report blockers only.
Do not modify code, push, reply to threads, enable auto-merge or merge.

How to read this workflow

Interrogate does not automatically apply findings. Babysit can handle conflicts, review threads and CI when you authorize active work, but it stops at merge-ready. Shipping is the separate workflow that independently verifies and lands the contiguous verified part of a stack. R6R8

Expected evidence: A reasoned review and a precise PR state. For later active babysitting, explicitly authorize pushes and review replies while still forbidding merge. For landing, give a separate explicit instruction.
08Run a bounded task, then audit or resume itAn internal migration with a checkable stopping condition
Figure-it-out + decision trail · host loop · session pickup

Use this only after the local verification procedure works. Define permissible actions and failure behavior before leaving the agent unattended.

Cursor chat · example prompt
/poteto-mode continue the approved internal API migration in its isolated worktree.
Done means zero old runtime callers, passing migration fixtures and verified UI flows.
Local edits, tests and local commits are allowed. No push, PR, merge, deployment,
production data access, dependency upgrades or messages to other people.
Keep a decision trail with commands and evidence paths.
Stop after three failed approaches without measurable progress, or when access,
credentials or an irreversible decision blocks you. Do not relax the checks.
Use the host's loop mechanism only if it is available and confirmed active.

How to read this workflow

The repository uses Cursor’s /loop as the wake mechanism; it is not a pstack-provided scheduler. The stop-after-three rule is a suggested human boundary, not the plugin’s default. An active host, usable tools and sufficient allowance are still required. R11R3

Expected evidence: A current completion status, local commits, the durable decision log and an Attention summary naming what you should inspect. Missing capability or verification is BLOCKED, not success.
Cursor chat · audit and resume as separate requests
/show-me-your-work summarize this run. Start with the Attention section.

When resuming later:
/poteto-mode take over this branch. Read the decision log and inspect current state.
Verify inherited claims, name the resume point and do not repeat completed work.
Keep the previous local-only permission boundary.
No matching workflow. Try a broader term or select All.
i
Parallel code work needs more than separate prompts

Use separate branches/worktrees for independent edits, and isolate ports, browser profiles, data directories and fixtures as needed. For one tightly coupled feature, the documented playbook favors a single owner who delegates within the work rather than several competing top-level owners. R9R10R12

When do the heavier workflows earn their place?

Autopilot-stack builds and verifies a linear stack for you to review and land. Autopilot-full can run independent PRs through verified merging. Orchestrate is for a standing, multi-day program with a coordinator and many subagents.

These are not starting requirements for a small app or a single bug. Use explicit authorization for any workflow that publishes or merges. “Don’t ship” does not automatically mean “don’t create remote PRs”; specify both when both are prohibited. R11

Keep the human in charge

Guardrails that matter in real repositories.

pstack’s defaults are deliberately proactive. Use actual host permissions and project protections alongside the written brief.

Permissions

Separate edit, publish and land.

The mode allows broad reversible actions and external actions by default. The source says to pause for irreversible actions, but also has autonomy overrides. Do not rely on a vague “be careful.” Name which actions are allowed and forbidden. R3

Model usage

Parallelism is not free.

Panels and workers create additional model work. A narrow scope and smaller panel can limit fan-out; inheriting the parent model does not eliminate it. Usage depends on the host, selected models and actual run. No fixed cost is promised here. R4R6

Environment

Use non-production proof.

Give verification isolated accounts, fixtures and instances. Inspect side effects even for a “dry run.” Cleanup should remove only what the run created and preserve its evidence. R9

Trust

Agreement is not correctness.

Independent reviews help expose blind spots. They do not guarantee a bug-free result. Read the dismissals, inspect the change and demand the relevant executable checks. R6R8

Reusable boundary · append to your task prompt
For this task, allow repository reads, isolated local app runs, focused edits,
tests and local commits. Preserve unrelated work.
Do not push, create or merge PRs, enable auto-merge, force-push, deploy,
change production data, contact customers or post to team channels.
Use only authorized project sources and test credentials.
When blocked, report the evidence and stop rather than inventing success.

Common mistakes and the better move

MistakeBetter move
“Build my entire app.”One runnable slice, explicit non-goals, and a real verification path.
Generating verification for an app that does not start.Fix or report the baseline blocker first. The generator requires a usable checkout.
Telling every worker to edit the same checkout.Separate worktrees and runtime state, or serialize genuinely shared writes.
“Work on this all night.”A pass/fail finish condition, allowed actions, a log and an escape hatch.
Using architect as though it only produces a document.Say with checkpoint and explicitly stop before implementation.
Accepting “tests pass” as the entire handoff.Inspect what was tested, what was not, and the changed behavior on the right surface.
Running aggressive cleanup across unrelated legacy code.Limit cleanup to the task’s diff and protect required public behavior and compatibility.

Can I use the same instructions in another coding agent?

The author’s indexed article says pstack can work with agentic coding tools beyond Cursor. But the repository you linked is a Cursor-native plugin: it names Cursor installation, model rules, tool primitives, subagents, built-ins and companion skills. X4R1R2R3

Portable Markdown does not guarantee drop-in runtime compatibility. This guide documents the upstream Cursor path, not a validated port. For another host, first verify skill discovery, subagent mapping, model names, control tools, history access and loop support. Do not assume Cursor chat commands are shell commands or valid commands in another product.

The skill is missing in a Cloud Agent. Is my repository broken?

Not necessarily. Cursor staff acknowledged a cloud-plugin loading problem on August 28, 2026; the retrieved thread includes a September 2 follow-up but no confirmed resolution. Staff said local agents were unaffected by that report. This is a dated incident, not proof that every cloud session is currently broken. F1

For first adoption, use a local agent with confirmed skill loading. Check the linked thread and your current runtime before relying on cloud execution. Copying only poteto-mode/SKILL.md can omit its referenced playbooks and companion capabilities; do not mistake that partial copy for the full plugin.

Should I create my own mode immediately?

Start by learning what the default mode does on a few real tasks. Then use /automate-me to capture repeated preferences, and /reflect to improve a workflow after a useful lesson. Review the resulting changes rather than blindly accumulating rules. R1

Keep project-specific knowledge in the project. Make recurrent correctness requirements executable where possible, such as a test or a lint rule, rather than adding another reminder paragraph. R3X5
